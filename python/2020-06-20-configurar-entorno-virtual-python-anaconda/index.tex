\abstract{Esta publicación presenta una guía práctica y detallada para
la creación, gestión y mantenimiento de entornos virtuales aislados
utilizando Conda (y Mamba como acelerador), orientada especialmente a
economistas, investigadores y científicos de datos que manejan múltiples
proyectos académicos y de automatización. Se explica la filosofía detrás
de los entornos separados, se propone una estrategia concreta de
entornos por propósito (econblog, scripts-env, datascience, teaching), y
se documentan paso a paso; creación de entornos específicos, selección
cuidadosa de paquetes (tanto de conda-forge como vía pip), generación y
mantenimiento de archivos environment.yml reproducibles, integración
óptima con JupyterLab, VS Code y Quarto, configuración de alias para
flujos de trabajo eficientes, mejores prácticas para colaboración y
reproducibilidad, y resolución de problemas frecuentes. El enfoque
prioriza evitar conflictos de dependencias, garantizar la
reproducibilidad de análisis econométricos y publicaciones académicas, y
mantener un sistema ligero y organizado. }

\subsection{1. Conceptos fundamentales: bibliotecas y
repositorios}\label{conceptos-fundamentales-bibliotecas-y-repositorios}

Antes de gestionar entornos, conviene fijar dos términos que la
documentación oficial de conda distingue:

\begin{itemize}
\tightlist
\item
  \textbf{Canal (\emph{channel})}: una ubicación (típicamente una URL)
  donde se almacenan paquetes conda. El comando \texttt{conda} busca,
  por defecto, en un conjunto predeterminado de canales, y los paquetes
  se descargan y actualizan automáticamente desde el canal por defecto
  (\texttt{repo.anaconda.com/pkgs/}). El canal comunitario más usado
  para ciencia de datos es \textbf{\texttt{conda-forge}}.
\item
  \textbf{Entorno (\emph{environment})}: una biblioteca de paquetes
  aislada y autocontenida, con su propia versión de Python y su propio
  conjunto de paquetes, independiente de cualquier otro entorno o de la
  biblioteca de sistema.
\end{itemize}

\begin{center}\rule{0.5\linewidth}{0.5pt}\end{center}

\subsection{2. Filosofía de entornos
separados}\label{filosofuxeda-de-entornos-separados}

\textbf{El problema sin entornos}: sin aislamiento, todos los paquetes
comparten el mismo espacio. Esto provoca conflictos de versiones (por
ejemplo \texttt{pandas\ 1.5} vs \texttt{pandas\ 2.0} requeridos por
proyectos distintos), dependencias rotas al actualizar, imposibilidad de
reproducir análisis antiguos, y proyectos que interfieren entre sí.

\textbf{La solución}: un entorno aislado por proyecto o por tipo de
trabajo.

\subsubsection{\texorpdfstring{2.1. Principio fundamental: nunca
instalar paquetes en
\texttt{base}}{2.1. Principio fundamental: nunca instalar paquetes en base}}\label{principio-fundamental-nunca-instalar-paquetes-en-base}

El entorno \texttt{base} es el que conda activa por defecto al
inicializar la shell. Instalar paquetes de proyecto directamente ahí
termina, con el tiempo, recreando el mismo problema que los entornos
buscan evitar: un único espacio compartido y contaminado.

\begin{Shaded}
\begin{Highlighting}[]
\CommentTok{\# INCORRECTO}
\ExtensionTok{conda}\NormalTok{ activate base}
\ExtensionTok{mamba}\NormalTok{ install pandas   }\CommentTok{\# NO HACER ESTO}

\CommentTok{\# CORRECTO}
\ExtensionTok{conda}\NormalTok{ activate mi{-}proyecto}
\ExtensionTok{mamba}\NormalTok{ install pandas   }\CommentTok{\# instalar en el entorno específico}
\end{Highlighting}
\end{Shaded}

\texttt{base} debería contener, como máximo, conda/mamba mismos y
herramientas de gestión de entornos; nada de las dependencias de un
proyecto particular.

\subsubsection{2.2. Un entorno por propósito, no por proyecto
individual}\label{un-entorno-por-propuxf3sito-no-por-proyecto-individual}

No es necesario (ni conveniente) crear un entorno nuevo por cada
repositorio. La estrategia más sostenible es agrupar proyectos que
comparten el mismo conjunto de dependencias bajo un mismo entorno con
nombre temático (por ejemplo \texttt{econblog}, \texttt{scripts-env}),
reservando entornos dedicados para casos con requisitos claramente
distintos (paquetes pesados, versiones fijas para estudiantes, etc.).
Esto se desarrolla con detalle en la sección 21.

\begin{center}\rule{0.5\linewidth}{0.5pt}\end{center}

\subsection{3. Creación de entornos}\label{creaciuxf3n-de-entornos}

\subsubsection{3.1. Crear un entorno

\subsubsection{3.5. Crear un entorno con Python y múltiples paquetes a

\begin{Shaded}

\ExtensionTok{conda}\NormalTok{ create }\AttributeTok{{-}n}\NormalTok{ myenv python=3.9 scipy=0.17.3 astroid babel}

\begin{quote}
\textbf{Recomendación oficial importante}: instala todos los programas
que quieras en un entorno \textbf{al mismo tiempo}. Instalarlos uno por
uno, en comandos separados, puede provocar conflictos de dependencias
que un único comando de resolución conjunta evitaría.
\end{quote}

\subsubsection{3.6. Paquetes por defecto en cada entorno
nuevo}\label{paquetes-por-defecto-en-cada-entorno-nuevo}

Para que conda instale automáticamente pip (u otro programa) cada vez
que creas un entorno nuevo, agrega los paquetes por defecto a la sección
\texttt{create\_default\_packages} de tu archivo \texttt{.condarc}. Si
en un caso puntual no deseas esos paquetes por defecto:

\begin{Shaded}
\begin{Highlighting}[]
\ExtensionTok{conda}\NormalTok{ create }\AttributeTok{{-}{-}no{-}default{-}packages} \AttributeTok{{-}n}\NormalTok{ myenv python}
\end{Highlighting}
\end{Shaded}

\subsection{5. Ubicación de entornos: por nombre vs.~por
prefijo}\label{ubicaciuxf3n-de-entornos-por-nombre-vs.-por-prefijo}

\subsubsection{5.1. Entornos por nombre (comportamiento por
defecto)}\label{entornos-por-nombre-comportamiento-por-defecto}

Por defecto, los entornos creados con \texttt{-\/-name}/\texttt{-n}
viven en la carpeta \texttt{envs/} de tu instalación de conda (por
ejemplo \texttt{\textasciitilde{}/miniconda3/envs/}).

\subsubsection{5.2. Entornos por prefijo (ubicación
personalizada)}\label{entornos-por-prefijo-ubicaciuxf3n-personalizada}

Puedes controlar dónde vive un entorno indicando una ruta de destino con
\texttt{-\/-prefix}/\texttt{-p}:

\begin{Shaded}
\begin{Highlighting}[]
\ExtensionTok{conda}\NormalTok{ create }\AttributeTok{{-}{-}prefix}\NormalTok{ ./envs jupyterlab=3.2 matplotlib=3.5 numpy=1.21}
\end{Highlighting}
\end{Shaded}

Se activa igual que un entorno por nombre, pero usando la ruta:

\begin{Shaded}
\begin{Highlighting}[]
\ExtensionTok{conda}\NormalTok{ activate ./envs}
\end{Highlighting}
\end{Shaded}

\textbf{Ventajas documentadas oficialmente de usar \texttt{-\/-prefix}
dentro de la carpeta del proyecto}:

\begin{itemize}
\tightlist
\item
  Es fácil saber, con solo ver la estructura de carpetas, si tu proyecto
  usa un entorno aislado (aparece como subcarpeta).
\item
  El proyecto queda más autocontenido: todo, incluido el software
  requerido, vive dentro de un único directorio de proyecto.
\item
  Te permite reutilizar el mismo nombre de subcarpeta (por ejemplo
  \texttt{envs} o \texttt{env}) en todos tus proyectos, en vez de tener
  que inventar un nombre distinto para cada entorno.
\end{itemize}

\textbf{Consideraciones a tener en cuenta} si usas \texttt{-\/-prefix}:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  Conda ya no puede encontrar tu entorno con la bandera
  \texttt{-\/-name}; generalmente necesitarás pasar \texttt{-\/-prefix}
  junto con la ruta completa del entorno.
\item
  Tu prompt mostrará la ruta absoluta completa del entorno activo en vez
  de su nombre, lo cual puede resultar en prefijos largos en la
  terminal, por ejemplo:
\end{enumerate}

\begin{verbatim}
(/home/achalmaedison/Proyectos/mi-proyecto/envs) $
\end{verbatim}

Para evitar ese prefijo largo, ajusta la configuración
\texttt{env\_prompt} en tu \texttt{.condarc}:

\begin{Shaded}
\begin{Highlighting}[]
\ExtensionTok{conda}\NormalTok{ config }\AttributeTok{{-}{-}set}\NormalTok{ env\_prompt }\StringTok{\textquotesingle{}(\{name\})\textquotesingle{}}
\end{Highlighting}
\end{Shaded}

Esto edita (o crea) tu archivo \texttt{.condarc}, y a partir de ahí el
prompt mostrará solo el nombre genérico del entorno (el nombre de su
carpeta raíz):

\begin{verbatim}
$ cd project-directory
$ conda activate ./env
(env) project-directory $
\end{verbatim}

\subsection{6. Plataforma de destino de un
entorno}\label{plataforma-de-destino-de-un-entorno}

Por defecto, conda crea entornos dirigidos a la plataforma sobre la que
se está ejecutando. Puedes consultar tu plataforma actual con
\texttt{conda\ info} (campo \texttt{platform}).

En casos avanzados, puedes especificar una plataforma distinta con la
bandera \texttt{-\/-platform}, disponible en \texttt{conda\ create} y
\texttt{conda\ env\ create}. Por ejemplo, para crear un entorno
orientado a procesadores Intel desde una Mac con Apple Silicon (emulado
vía Rosetta):

\begin{Shaded}
\begin{Highlighting}[]
\ExtensionTok{conda}\NormalTok{ create }\AttributeTok{{-}{-}platform}\NormalTok{ osx{-}64 }\AttributeTok{{-}{-}name}\NormalTok{ python{-}x64 python}
\end{Highlighting}
\end{Shaded}

\begin{quote}
\textbf{Nota oficial}: no se puede especificar \texttt{-\/-platform}
para entornos ya existentes; una vez creado, el entorno queda anotado
con esa configuración y las operaciones posteriores recuerdan la
plataforma de destino. La documentación oficial también advierte que
especificar un sistema operativo distinto (por ejemplo, crear un entorno
Linux desde macOS) no se recomienda fuera de operaciones
\texttt{-\/-dry-run}, ya que suele fallar por paquetes virtuales
faltantes o por incompatibilidades de sistema de archivos.
\end{quote}

\subsection{7. Activación y
desactivación}\label{activaciuxf3n-y-desactivaciuxf3n}

\subsubsection{7.1. Qué hace realmente la
activación}\label{quuxe9-hace-realmente-la-activaciuxf3n}

Activar un entorno cumple dos funciones principales: añade entradas al
\texttt{PATH} correspondientes al entorno, y ejecuta cualquier script de
activación que el entorno pueda contener (estos scripts son cómo los
paquetes configuran variables de entorno arbitrarias necesarias para su
funcionamiento). La activación antepone rutas al \texttt{PATH} solo
mientras el entorno está activo en esa sesión de terminal; no es un
cambio global del sistema.

\begin{quote}
\textbf{Advertencia oficial importante}: durante la instalación de
Anaconda/Miniconda existe la opción ``Add Anaconda to my PATH
environment variable'' --- \textbf{no se recomienda usarla}, porque
\emph{añade} (append) Anaconda al PATH sin llamar a los scripts de
activación correspondientes. La forma correcta de integrar conda con tu
shell es \texttt{conda\ init} (ver sección 8), no esa casilla del
instalador.
\end{quote}

\subsubsection{7.2. Activar un entorno}\label{activar-un-entorno}

\begin{Shaded}
\begin{Highlighting}[]
\ExtensionTok{conda}\NormalTok{ activate myenv}
\end{Highlighting}
\end{Shaded}

(sustituye \texttt{myenv} por el nombre del entorno, o por la ruta si lo
creaste con \texttt{-\/-prefix}).

Si ves una advertencia indicando que el intérprete de Python está en un
entorno conda pero el entorno no fue activado correctamente, significa
que necesitas activar el entorno apropiadamente (en Windows, ejecutando
\texttt{c:\textbackslash{}Anaconda3\textbackslash{}Scripts\textbackslash{}activate}
si es necesario).

\begin{quote}
\textbf{Nota oficial sobre Windows}: Windows es especialmente sensible a
una activación correcta, porque su cargador de bibliotecas no soporta el
concepto de bibliotecas y ejecutables que saben dónde buscar sus propias
dependencias (RPATH, como sí ocurre en Linux/macOS). Windows depende en
cambio de un orden de búsqueda de bibliotecas de enlace dinámico. Si los
entornos no están activos correctamente, las bibliotecas no se
encontrarán y aparecerán muchos errores --- los errores de HTTP o SSL
son comunes cuando el Python de un entorno hijo no puede encontrar la
biblioteca OpenSSL necesaria.
\end{quote}

\subsubsection{7.3. Desactivar un entorno}\label{desactivar-un-entorno}

\begin{Shaded}
\begin{Highlighting}[]
\ExtensionTok{conda}\NormalTok{ deactivate}
\end{Highlighting}
\end{Shaded}

\begin{quote}
\textbf{Nota oficial}: para simplemente volver al entorno por defecto,
es mejor llamar a \texttt{conda\ activate} sin especificar ningún
entorno, en vez de intentar desactivar repetidamente. Si ejecutas
\texttt{conda\ deactivate} estando en tu entorno \texttt{base}, podrías
perder la capacidad de ejecutar \texttt{conda} en esa shell (no es
grave: es local a esa sesión, basta con abrir una nueva terminal). Sin
embargo, si el entorno fue activado con \texttt{-\/-stack} (o se apiló
automáticamente), sí es preferible usar \texttt{conda\ deactivate} para
deshacerlo correctamente.
\end{quote}

\subsubsection{7.4. Determinar tu entorno activo
actual}\label{determinar-tu-entorno-activo-actual}

Por defecto, el entorno activo se muestra entre paréntesis \texttt{()} o
corchetes \texttt{{[}{]}} al inicio de tu prompt:

\begin{verbatim}
(myenv) $
\end{verbatim}

Si no ves esto, ejecuta \texttt{conda\ info\ -\/-envs}; tu entorno
actual aparecerá marcado con un asterisco (\texttt{*}).

Para deshabilitar/habilitar que el nombre del entorno aparezca en el
prompt:

\begin{Shaded}
\begin{Highlighting}[]
\ExtensionTok{conda}\NormalTok{ config }\AttributeTok{{-}{-}set}\NormalTok{ changeps1 false   }\CommentTok{\# deshabilitar}
\ExtensionTok{conda}\NormalTok{ config }\AttributeTok{{-}{-}set}\NormalTok{ changeps1 true    }\CommentTok{\# rehabilitar}
\end{Highlighting}
\end{Shaded}

\subsection{\texorpdfstring{8. \texttt{conda\ init} e integración con
shells}{8. conda init e integración con shells}}\label{conda-init-e-integraciuxf3n-con-shells}

Versiones tempranas de conda requerían pasos manuales adicionales para
que \texttt{conda\ activate} funcionara correctamente. Conda 4.4
introdujo \texttt{conda\ activate}, y conda 4.6 añadió soporte de
inicialización extensivo para que conda funcione de forma más rápida y
menos disruptiva en una amplia variedad de shells: \textbf{bash, zsh,
csh, fish, xonsh, y más}. Esto es lo que ejecuta el instalador cuando
aceptas inicializar conda (ver guía de instalación).

\begin{quote}
\textbf{Relevante para tu configuración (zsh + kitty)}: dado que tu
shell por defecto es \texttt{zsh}, \texttt{conda\ init} detecta y
modifica \texttt{\textasciitilde{}/.zshrc} automáticamente. Si en algún
contexto necesitas integrar conda con \texttt{fish} además de
\texttt{zsh}, puedes ejecutar \texttt{conda\ init\ fish} adicionalmente;
ambas inicializaciones pueden coexistir.
\end{quote}

\subsubsection{\texorpdfstring{8.1. Inicialización mínima
(\texttt{-\/-condabin})}{8.1. Inicialización mínima (-\/-condabin)}}\label{inicializaciuxf3n-muxednima---condabin}

Si prefieres no instalar una función de shell completa en tu perfil,
\texttt{conda\ init\ -\/-condabin} añade únicamente el directorio
\texttt{\$CONDA\_PREFIX/condabin/} al \texttt{PATH}. Esa carpeta solo
contiene el ejecutable \texttt{conda}, por lo que es mínimamente
invasiva.

\subsubsection{8.2. Activación automática del entorno por
defecto}\label{activaciuxf3n-automuxe1tica-del-entorno-por-defecto}

El ajuste \texttt{auto\_activate} (booleano) controla si conda activa
automáticamente el entorno por defecto cada vez que arranca tu shell. El
comando \texttt{conda} estará disponible de cualquier forma, pero sin
activar el entorno, ningún otro programa del entorno por defecto estará
disponible hasta que lo actives explícitamente con
\texttt{conda\ activate}.

El entorno a activar por defecto se configura con:

\begin{Shaded}
\begin{Highlighting}[]
\ExtensionTok{default\_activation\_env:}\NormalTok{ str}
\end{Highlighting}
\end{Shaded}

\begin{quote}
Algunas personas desactivan \texttt{auto\_activate} para acelerar el
arranque de su shell, o para evitar que software instalado vía conda
oculte automáticamente otro software del sistema.
\end{quote}

\begin{center}\rule{0.5\linewidth}{0.5pt}\end{center}

\subsection{\texorpdfstring{9. Activación anidada
(\emph{stacking})}{9. Activación anidada (stacking)}}\label{activaciuxf3n-anidada-stacking}

Por defecto, \texttt{conda\ activate} \textbf{desactiva} el entorno
actual antes de activar el nuevo, y lo reactiva al desactivar el nuevo.
A veces interesa conservar las entradas de \texttt{PATH} del entorno
actual para seguir teniendo acceso fácil a programas de línea de
comandos de ese primer entorno (común cuando ciertas utilidades están
instaladas en el entorno por defecto).

Para conservar el entorno actual en el \texttt{PATH} al activar uno
nuevo:

\begin{Shaded}
\begin{Highlighting}[]
\ExtensionTok{conda}\NormalTok{ activate }\AttributeTok{{-}{-}stack}\NormalTok{ myenv}
\end{Highlighting}
\end{Shaded}

Para que esto ocurra automáticamente siempre que actives un entorno
desde el entorno más externo (típicamente el entorno por defecto):

\begin{Shaded}
\begin{Highlighting}[]
\ExtensionTok{conda}\NormalTok{ config }\AttributeTok{{-}{-}set}\NormalTok{ auto\_stack 1}
\end{Highlighting}
\end{Shaded}

Puedes especificar un número mayor para permitir niveles más profundos
de apilamiento automático, aunque la documentación \textbf{no lo
recomienda}, ya que niveles más profundos de stacking tienden a generar
confusión.

\subsection{10. Gestión de canales}\label{gestiuxf3n-de-canales}

\subsubsection{10.1. Qué son y cómo se resuelven
colisiones}\label{quuxe9-son-y-cuxf3mo-se-resuelven-colisiones}

Los canales son las ubicaciones donde se almacenan los paquetes.
Distintos canales pueden tener el mismo paquete, por lo que conda debe
resolver estas colisiones. No hay colisiones si usas únicamente el canal
por defecto, ni si todos tus canales contienen paquetes que no se
solapan entre sí.

Cuando hay colisión, conda procesa los paquetes con el mismo nombre
across todos los canales listados de la siguiente forma:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  Ordena los paquetes de mayor a menor prioridad de canal.
\item
  Entre paquetes empatados en prioridad de canal, ordena de mayor a
  menor número de versión.
\item
  Entre paquetes aún empatados (mismo canal, misma versión), ordena de
  mayor a menor número de build.
\item
  Instala el primer paquete de la lista ordenada que satisface las
  especificaciones de instalación.
\end{enumerate}

\subsubsection{10.2. Agregar un canal}\label{agregar-un-canal}

Para añadir un canal al principio de la lista (máxima prioridad):

\begin{Shaded}
\begin{Highlighting}[]
\ExtensionTok{conda}\NormalTok{ config }\AttributeTok{{-}{-}add}\NormalTok{ channels new\_channel}
\end{Highlighting}
\end{Shaded}

(equivalente explícito:
\texttt{conda\ config\ -\/-prepend\ channels\ new\_channel}).

Para añadirlo al final (mínima prioridad):

\begin{Shaded}
\begin{Highlighting}[]
\ExtensionTok{conda}\NormalTok{ config }\AttributeTok{{-}{-}append}\NormalTok{ channels new\_channel}
\end{Highlighting}
\end{Shaded}

\subsubsection{10.3. Prioridad estricta de canales
(recomendada)}\label{prioridad-estricta-de-canales-recomendada}

Desde la versión 4.6.0, conda ofrece la función de \textbf{prioridad
estricta de canales}, que puede acelerar dramáticamente las operaciones
de conda y reducir problemas de incompatibilidad entre paquetes. La
documentación oficial \textbf{recomienda activar \texttt{strict} cuando
sea posible}:

\begin{Shaded}
\begin{Highlighting}[]
\ExtensionTok{conda}\NormalTok{ config }\AttributeTok{{-}{-}set}\NormalTok{ channel\_priority strict}
\end{Highlighting}
\end{Shaded}

Valores posibles de \texttt{channel\_priority}:

\begin{itemize}
\tightlist
\item
  \texttt{strict}: los paquetes en canales de menor prioridad ni
  siquiera se consideran si el mismo paquete existe en un canal de mayor
  prioridad.
\item
  \texttt{flexible} (valor por defecto): el solver puede buscar en
  canales de menor prioridad para satisfacer dependencias, en vez de
  fallar con un error de no-satisfacibilidad.
\item
  \texttt{disabled}: la versión del paquete tiene precedencia; la
  prioridad de canal configurada solo se usa para desempatar.
\end{itemize}

\subsubsection{\texorpdfstring{10.4. Canal por defecto de tu proyecto:
\texttt{conda-forge}}{10.4. Canal por defecto de tu proyecto: conda-forge}}\label{canal-por-defecto-de-tu-proyecto-conda-forge}

Siguiendo la convención que ya usas en tus \texttt{environment.yml}
(econblog, scripts-env, etc.), \texttt{conda-forge} es el canal
comunitario estándar para ciencia de datos en el ecosistema conda, con
una cobertura de paquetes mucho más amplia que el canal
\texttt{defaults} de Anaconda Inc.~Puedes especificar un canal puntual
para un solo paquete dentro de un \texttt{environment.yml} con la
sintaxis \texttt{canal::paquete}, sin necesidad de que ese canal esté en
la lista \texttt{channels:} general (ver sección 22 para ejemplos
completos).

\subsection{12. Conda y pip: cómo combinarlos
correctamente}\label{conda-y-pip-cuxf3mo-combinarlos-correctamente}

Es habitual necesitar paquetes que solo existen en PyPI (no en
conda-forge ni en el canal por defecto). La documentación oficial es
explícita sobre el orden y la disciplina necesarios para que esto no
genere conflictos.

\subsubsection{12.1. Instalar pip dentro de un entorno
conda}\label{instalar-pip-dentro-de-un-entorno-conda}

\begin{Shaded}
\begin{Highlighting}[]
\ExtensionTok{conda}\NormalTok{ install }\AttributeTok{{-}n}\NormalTok{ myenv pip}
\ExtensionTok{conda}\NormalTok{ activate myenv}
\ExtensionTok{pip} \OperatorTok{\textless{}}\NormalTok{subcomando{-}de{-}pip}\OperatorTok{\textgreater{}}
\end{Highlighting}
\end{Shaded}

\subsubsection{12.2. Reglas oficiales para combinar conda y
pip}\label{reglas-oficiales-para-combinar-conda-y-pip}

\textbf{Usa pip solo después de conda:} - Instala tantos requisitos como
sea posible con conda, y usa pip solo para lo que falte. - pip debería
ejecutarse con \texttt{-\/-upgrade-strategy\ only-if-needed} (que es, de
hecho, el comportamiento por defecto). - No uses pip con el argumento
\texttt{-\/-user}; evita instalaciones ``para todos los usuarios''.

\textbf{Usa entornos conda para aislamiento:} - Crea un entorno conda
específicamente para aislar cualquier cambio que haga pip. - Los
entornos ocupan poco espacio adicional gracias a los \emph{hard links}
que usa conda internamente. - Ten cuidado de no ejecutar pip en el
entorno raíz/\texttt{base}.

\textbf{Recrea el entorno si necesitas hacer cambios:} - Una vez que pip
ha sido usado, conda \textbf{ya no es consciente} de esos cambios. -
Para instalar paquetes conda adicionales después de haber usado pip, lo
más seguro es \textbf{recrear el entorno} desde cero, en vez de
simplemente correr conda de nuevo encima.

\textbf{Guarda los requisitos de conda y pip en archivos de texto:} -
Los requisitos de conda pueden pasarse vía el argumento
\texttt{-\/-file}. - pip acepta una lista de paquetes Python con
\texttt{-r}/\texttt{-\/-requirements}. - \texttt{conda\ env} exporta o
crea entornos basados en un archivo combinado de requisitos conda y pip
(ver sección 22).

\subsubsection{12.3. Orden correcto en la
práctica}\label{orden-correcto-en-la-pruxe1ctica}

\begin{Shaded}
\begin{Highlighting}[]
\ExtensionTok{mamba}\NormalTok{ install pandas matplotlib }\AttributeTok{{-}y}   \CommentTok{\# 1. primero conda/mamba}
\ExtensionTok{pip}\NormalTok{ install wooldridge               }\CommentTok{\# 2. luego pip, solo lo que falte}

\CommentTok{\# NUNCA mezclar en el mismo comando o cadena:}
\CommentTok{\# conda install pandas \&\& pip install wooldridge   \# evitar este patrón}
\end{Highlighting}
\end{Shaded}

\subsection{13. Actualizar un entorno
existente}\label{actualizar-un-entorno-existente}

Puede que necesites actualizar tu entorno por varias razones: una
dependencia central lanzó una nueva versión, necesitas un paquete
adicional para un análisis, o encontraste un paquete mejor y ya no
necesitas el anterior.

En cualquiera de estos casos, actualiza el contenido de tu
\texttt{environment.yml} y luego ejecuta:

\begin{Shaded}
\begin{Highlighting}[]
\ExtensionTok{conda}\NormalTok{ env update }\AttributeTok{{-}{-}file}\NormalTok{ environment.yml }\AttributeTok{{-}{-}prune}
\end{Highlighting}
\end{Shaded}

\begin{quote}
\textbf{Nota oficial sobre \texttt{-\/-prune}}: esta opción hace que
conda elimine del entorno cualquier dependencia que ya no sea requerida
según el archivo actualizado. Sin \texttt{-\/-prune}, los paquetes
removidos del \texttt{environment.yml} permanecerían instalados aunque
ya no estén declarados.
\end{quote}

\begin{center}\rule{0.5\linewidth}{0.5pt}\end{center}

\subsection{14. Congelar un entorno (frozen
environments)}\label{congelar-un-entorno-frozen-environments}

Una función relativamente reciente del estándar conda (CEP 22) introduce
un archivo marcador de entorno que indica a conda que \textbf{no permita
modificaciones} en un entorno dado.

Al intentar añadir, actualizar o eliminar un paquete en un entorno
congelado, obtendrás por defecto un error:

\begin{verbatim}
EnvironmentIsFrozenError: Cannot not modify '~/.conda/envs/my-env'.
The environment is marked as frozen. You can ignore this error with
the `--override-frozen` flag, at your own risk.
\end{verbatim}

Es posible pasar la bandera \texttt{-\/-override-frozen} para forzar la
modificación, pero la documentación oficial \textbf{no lo recomienda}:
solo debería usarse por usuarios avanzados conscientes de los riesgos y
capaces de resolver las posibles complicaciones derivadas de esa
operación.

\begin{quote}
\textbf{Caso de uso relevante para ti}: esto encaja con tu entorno
\texttt{teaching}, donde quieres versiones estables y probadas para tus
estudiantes; congelar ese entorno una vez validado evita modificaciones
accidentales que rompan el material de clase a mitad de semestre.
\end{quote}

\begin{center}\rule{0.5\linewidth}{0.5pt}\end{center}

\subsection{15. Clonar un entorno}\label{clonar-un-entorno}

Para hacer una copia exacta de un entorno existente:

\begin{Shaded}
\begin{Highlighting}[]
\ExtensionTok{conda}\NormalTok{ create }\AttributeTok{{-}{-}name}\NormalTok{ myclone }\AttributeTok{{-}{-}clone}\NormalTok{ myenv}
\end{Highlighting}
\end{Shaded}

(sustituye \texttt{myclone} por el nombre del nuevo entorno, y
\texttt{myenv} por el entorno existente a copiar).

Verificar que la copia se haya creado:

\begin{Shaded}
\begin{Highlighting}[]
\ExtensionTok{conda}\NormalTok{ info }\AttributeTok{{-}{-}envs}
\end{Highlighting}
\end{Shaded}

Deberías ver ambos entornos ---el original y la copia nueva--- en la
lista.

\begin{quote}
\textbf{Uso práctico}: clonar es ideal para experimentar con cambios
riesgosos (por ejemplo, probar una actualización mayor de
\texttt{pandas} o \texttt{statsmodels}) sin arriesgar tu entorno de
producción; si el experimento sale mal, simplemente eliminas el clon.
\end{quote}

\subsubsection{\texorpdfstring{16.2. Compatibilidad multiplataforma con
\texttt{-\/-from-history}}{16.2. Compatibilidad multiplataforma con -\/-from-history}}\label{compatibilidad-multiplataforma-con---from-history}

Para máxima portabilidad entre sistemas operativos (por ejemplo,
exportar desde Kubuntu y restaurar en Windows), usa
\texttt{-\/-from-history}:

\begin{Shaded}
\begin{Highlighting}[]
\ExtensionTok{conda}\NormalTok{ export }\AttributeTok{{-}{-}from{-}history} \AttributeTok{{-}{-}format}\OperatorTok{=}\NormalTok{environment{-}yaml}
\end{Highlighting}
\end{Shaded}

Esto exporta \textbf{únicamente los paquetes que instalaste
explícitamente}, excluyendo dependencias específicas de plataforma que
se resolvieron automáticamente. Si creas un entorno e instalas, por
ejemplo, \texttt{python=3.7} y \texttt{codecov}, conda descargará e
instalará numerosos paquetes adicionales para resolver dependencias;
muchos de esos paquetes auxiliares podrían no ser compatibles entre
plataformas. \texttt{-\/-from-history} exporta solo lo que tú elegiste
explícitamente:

\begin{Shaded}
\begin{Highlighting}[]
\FunctionTok{name}\KeywordTok{:}\AttributeTok{ env{-}name}
\FunctionTok{channels}\KeywordTok{:}
\AttributeTok{  }\KeywordTok{{-}}\AttributeTok{ conda{-}forge}
\AttributeTok{  }\KeywordTok{{-}}\AttributeTok{ defaults}
\FunctionTok{dependencies}\KeywordTok{:}
\AttributeTok{  }\KeywordTok{{-}}\AttributeTok{ python=3.7}
\AttributeTok{  }\KeywordTok{{-}}\AttributeTok{ codecov}
\FunctionTok{prefix}\KeywordTok{:}\AttributeTok{ /Users/username/anaconda3/envs/env{-}name}
\end{Highlighting}
\end{Shaded}

\begin{quote}
\textbf{Nota oficial}: la bandera \texttt{-\/-from-history} solo
funciona con formatos estructurados (\texttt{environment-yaml},
\texttt{environment-json}); no es compatible con los formatos de texto
(\texttt{explicit}, \texttt{requirements}).
\end{quote}

\texttt{conda\ env\ export}}{16.3. El comando tradicional conda env export}}\label{el-comando-tradicional-conda-env-export}

También puedes usar el comando tradicional, exclusivo para YAML:

\begin{Shaded}
\begin{Highlighting}[]
\ExtensionTok{conda}\NormalTok{ activate myenv}
\ExtensionTok{conda}\NormalTok{ env export }\OperatorTok{\textgreater{}}\NormalTok{ environment.yml}
\end{Highlighting}
\end{Shaded}

\begin{quote}
\textbf{Advertencia oficial}: si ya tienes un archivo
\texttt{environment.yml} en tu directorio actual, será
\textbf{sobrescrito} durante esta operación. Este archivo gestiona tanto

\end{quote}

\subsubsection{\texorpdfstring{16.4. Crear un \texttt{environment.yml}
manualmente}{16.4. Crear un environment.yml manualmente}}\label{crear-un-environment.yml-manualmente}

También puedes escribir el archivo a mano, sin exportar desde un entorno
existente:

\textbf{Ejemplo simple:}

\begin{Shaded}
\begin{Highlighting}[]
\FunctionTok{name}\KeywordTok{:}\AttributeTok{ stats}
\FunctionTok{dependencies}\KeywordTok{:}
\AttributeTok{  }\KeywordTok{{-}}\AttributeTok{ numpy}
\AttributeTok{  }\KeywordTok{{-}}\AttributeTok{ pandas}
\end{Highlighting}
\end{Shaded}

\textbf{Ejemplo más completo, con canal específico por paquete y sección
pip:}

\begin{Shaded}
\begin{Highlighting}[]
\FunctionTok{name}\KeywordTok{:}\AttributeTok{ stats2}
\FunctionTok{channels}\KeywordTok{:}
\AttributeTok{  }\KeywordTok{{-}}\AttributeTok{ javascript}
\FunctionTok{dependencies}\KeywordTok{:}
\AttributeTok{  }\KeywordTok{{-}}\AttributeTok{ python=3.9}
\AttributeTok{  }\KeywordTok{{-}}\AttributeTok{ bokeh=2.4.2}
\AttributeTok{  }\KeywordTok{{-}}\AttributeTok{ conda{-}forge::numpy=1.21.*}
\AttributeTok{  }\KeywordTok{{-}}\AttributeTok{ nodejs=16.13.*}
\AttributeTok{  }\KeywordTok{{-}}\AttributeTok{ flask}
\AttributeTok{  }\KeywordTok{{-}}\AttributeTok{ pip}
\AttributeTok{  }\KeywordTok{{-}}\AttributeTok{ }\FunctionTok{pip}\KeywordTok{:}
\AttributeTok{    }\KeywordTok{{-}}\AttributeTok{ Flask{-}Testing}
\end{Highlighting}
\end{Shaded}

\textbf{Notas sobre esta sintaxis (oficiales):}

\begin{itemize}
\tightlist
\item
  El uso del comodín \texttt{*} (por ejemplo \texttt{1.21.*}) mantiene
  fijas las versiones mayor y menor, permitiendo cualquier número de
  parche; esto te da actualizaciones de errores (\emph{bugfixes}) sin
  perder consistencia en el entorno.
\item
  La sintaxis \texttt{canal::paquete} permite especificar de qué canal
  instalar un paquete puntual, sin necesidad de que ese canal aparezca
  en la lista \texttt{channels:} general --- útil si quieres que
  \textbf{solo algunos} paquetes (no todos) vengan de un canal
  comunitario como conda-forge.
\item
  Puedes excluir los canales por defecto agregando \texttt{nodefaults} a
  la lista de canales:
\end{itemize}

\begin{Shaded}
\begin{Highlighting}[]
\FunctionTok{channels}\KeywordTok{:}
\AttributeTok{  }\KeywordTok{{-}}\AttributeTok{ javascript}
\AttributeTok{  }\KeywordTok{{-}}\AttributeTok{ nodefaults}
\end{Highlighting}
\end{Shaded}

Esto equivale a pasar \texttt{-\/-override-channels} a la mayoría de
comandos \texttt{conda}. Agregar \texttt{nodefaults} en un
\texttt{environment.yml} afecta solo a ese entorno, mientras que quitar
\texttt{defaults} de tu \texttt{.condarc} afectaría a todos tus
entornos.

\subsection{17. Construir entornos idénticos con especificaciones
explícitas}\label{construir-entornos-iduxe9nticos-con-especificaciones-expluxedcitas}

Para reproducir un entorno de forma exacta en la \textbf{misma
plataforma de sistema operativo} (misma máquina u otra distinta):

\subsubsection{17.1. Generar la especificación
explícita}\label{generar-la-especificaciuxf3n-expluxedcita}

\begin{Shaded}
\begin{Highlighting}[]
\ExtensionTok{conda}\NormalTok{ list }\AttributeTok{{-}{-}explicit}
\end{Highlighting}
\end{Shaded}

Esto produce una lista como:

\begin{verbatim}
# This file may be used to create an environment using:
# $ conda create --name <env> --file <this file>
# platform: osx-64
@EXPLICIT
https://repo.anaconda.com/pkgs/free/osx-64/mkl-11.3.3-0.tar.bz2
https://repo.anaconda.com/pkgs/free/osx-64/numpy-1.11.1-py35_0.tar.bz2
...
\end{verbatim}

Guardarlo en un archivo:

\begin{Shaded}
\begin{Highlighting}[]
\ExtensionTok{conda}\NormalTok{ list }\AttributeTok{{-}{-}explicit} \OperatorTok{\textgreater{}}\NormalTok{ spec{-}file.txt}
\end{Highlighting}
\end{Shaded}

\begin{quote}
\textbf{Nota oficial}: un archivo de especificación explícita
normalmente \textbf{no es multiplataforma}; por eso incluye un
comentario como \texttt{\#\ platform:\ osx-64} indicando dónde se generó
y dónde se sabe que funciona. En otras plataformas, los paquetes
listados podrían no estar disponibles, o faltar dependencias para
algunos paquetes clave.
\end{quote}

\subsubsection{17.2. Usar el archivo para crear un entorno
idéntico}\label{usar-el-archivo-para-crear-un-entorno-iduxe9ntico}

\begin{Shaded}
\begin{Highlighting}[]
\ExtensionTok{conda}\NormalTok{ create }\AttributeTok{{-}{-}name}\NormalTok{ myenv }\AttributeTok{{-}{-}file}\NormalTok{ spec{-}file.txt}
\end{Highlighting}
\end{Shaded}

O para instalar esos paquetes dentro de un entorno ya existente:

\begin{Shaded}
\begin{Highlighting}[]
\ExtensionTok{conda}\NormalTok{ install }\AttributeTok{{-}{-}name}\NormalTok{ myenv }\AttributeTok{{-}{-}file}\NormalTok{ spec{-}file.txt}
\end{Highlighting}
\end{Shaded}

\begin{quote}
Conda \textbf{no verifica} arquitectura ni dependencias al instalar
desde un archivo de especificación. Para asegurar que funcione
correctamente, el archivo debe haberse generado desde un entorno
funcional, y usarse en la misma arquitectura, sistema operativo y
plataforma (por ejemplo \texttt{linux-64} o \texttt{osx-64}).
\end{quote}

\subsubsection{17.3. Generar lockfiles explícitos sin crear un
entorno}\label{generar-lockfiles-expluxedcitos-sin-crear-un-entorno}

Si solo necesitas el archivo de bloqueo (\emph{lockfile}) sin tener que
crear y luego borrar un entorno temporal, puedes invocar conda en modo
JSON y procesar la salida con \texttt{jq} (necesitas tener \texttt{jq}
instalado, por ejemplo vía \texttt{conda\ create\ -n\ jq\ jq} o el
gestor de paquetes de tu sistema):

\textbf{Linux/macOS:}

\begin{Shaded}
\begin{Highlighting}[]
\BuiltInTok{echo} \StringTok{"@EXPLICIT"} \OperatorTok{\textgreater{}}\NormalTok{ explicit.txt}
\VariableTok{CONDA\_PKGS\_DIRS}\OperatorTok{=}\VariableTok{$(}\FunctionTok{mktemp} \AttributeTok{{-}d}\VariableTok{)} \ExtensionTok{conda}\NormalTok{ create }\AttributeTok{{-}{-}dry{-}run}\NormalTok{ MATCHSPECS\_AQUI }\AttributeTok{{-}{-}json} \KeywordTok{|} \ExtensionTok{jq} \AttributeTok{{-}r} \StringTok{\textquotesingle{}.actions.FETCH[] | .url + "\#" + .md5\textquotesingle{}} \OperatorTok{\textgreater{}\textgreater{}}\NormalTok{ explicit.txt}
\end{Highlighting}
\end{Shaded}

El archivo \texttt{explicit.txt} resultante puede usarse para crear un
nuevo entorno:

\begin{Shaded}
\begin{Highlighting}[]
\ExtensionTok{conda}\NormalTok{ create }\AttributeTok{{-}n}\NormalTok{ new{-}environment }\AttributeTok{{-}{-}file}\NormalTok{ explicit.txt}
\end{Highlighting}
\end{Shaded}

variables al activar un entorno, puedes crear scripts dedicados.

\textbf{En Linux/macOS:}

\begin{Shaded}
\begin{Highlighting}[]
\BuiltInTok{cd} \VariableTok{$CONDA\_PREFIX}

\FunctionTok{touch}\NormalTok{ ./etc/conda/deactivate.d/env\_vars.sh}
\end{Highlighting}

\begin{Shaded}
\begin{Highlighting}[]
\CommentTok{\#!/bin/sh}

\end{Highlighting}

\subsection{26. Mamba como acelerador}\label{mamba-como-acelerador}

\texttt{mamba} es una reimplementación del solucionador (\emph{solver})
de dependencias de conda, compatible en sintaxis con \texttt{conda} (la
mayoría de comandos \texttt{conda\ install}/\texttt{conda\ create}
funcionan igual con \texttt{mamba\ install}/\texttt{mamba\ create}),
pero significativamente más rápida para resolver entornos complejos. Es
ampliamente usado precisamente para los casos de esta guía: entornos con
muchos paquetes y dependencias cruzadas (como \texttt{econblog} o
\texttt{datascience}), donde el solver clásico de conda puede tardar
considerablemente más.

\begin{Shaded}
\begin{Highlighting}[]

\ExtensionTok{mamba}\NormalTok{ install paquete }\AttributeTok{{-}y}
\ExtensionTok{mamba}\NormalTok{ update }\AttributeTok{{-}{-}all} \AttributeTok{{-}y}
\end{Highlighting}
\end{Shaded}

Para la documentación oficial completa de mamba, consulta
mamba.readthedocs.io (ver sección de referencias).
